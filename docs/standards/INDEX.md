# 规范来源与沉淀台账

> 本文件由负责人维护,agent 只读。

## 1. 原则
- **目前没有公司手册。** 以行业规范为基线,在项目中不断补充,沉淀成公司自己的规范。
- **优先级:** 公司沉淀的"正式"条目 > "试行"条目 > 行业基线条目。冲突时以沉淀条目为准,并在 §3 台账里记录原因。
- **规则编号永不复用。** 废弃的条目保留编号,状态改为"废弃",写明原因。
- **状态含义:**
  - 试行:新加入的条目。**同样必须遵守**,遇到问题提"规范建议"。
  - 正式:经过至少一个完整里程碑,被遵守且没有被提出问题,由我转正。
  - 废弃:不再适用,保留记录。
- **行业基线条目**(P1–P18、D1–D34、T1–T20)初始状态统一为"试行"。

- **声明:** 本仓库的规范清单是对行业规范的提炼,**不等于已通过任何标准的合规认证**。官方链接、标准原文和条款对应补齐之前,不得据此宣称"符合某某标准"。

## 4. 沉淀流程
1. **发现**:除维护角色外(它写在自己的 proposals 里),任何角色发现规则缺漏、不适用或可优化,在 `docs/issues.md` 提"规范建议",写明:哪一条或新增、问题、建议改成什么、依据(行业来源或具体事件)。
2. **汇总**:里程碑复盘时,维护 agent 读这些建议,在 `docs/proposals/` 出修订建议。
3. **审核**:我决定采纳或拒绝。采纳的:我修改规范文件,新增条目的编号延续(如 D35),状态填"试行",在本台账登记,把 issues 对应条目标"已采纳"。
4. **转正**:试行条目经过一个完整里程碑后,没有被提出问题,我改为"正式",填转正日期。
5. **废弃**:状态改"废弃",保留编号,写明原因。
6. **门槛**:同类问题出现两次以上才新增条目,避免规则越堆越多。
7. **核对来源版本**:每半年,或技术栈变化时,核对一次 §2 里各来源的现行版本,补全官方链接、核对日期和条款对应。
