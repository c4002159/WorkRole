# 产品规范清单

> 本清单由我根据通行做法整理,参考方向:ISO/IEC/IEEE 29148(需求工程)、GB/T 8567(软件文档编制)。
> 目前没有公司产品规范,本清单以行业规范为基线。来源版本的核对情况、条目状态(试行/正式/废弃)和沉淀流程见 `INDEX.md`。新增条目编号延续(P19 起)。

## 1. 需求描述
- P1 一条需求只说一件事,以"谁在什么情况下能做什么"的句式书写。
- P2 禁止无法验证的词:等、相关、适当、快速、友好、尽量、合理。要写具体数值或条件。
- P3 每条需求有编号、优先级(必须/应该/可以)、来源(指向 00 的条目)。
- P4 每条功能需求有验收标准,写成三段:前置条件 / 操作 / 预期结果(可对应 GIVEN / WHEN / THEN 写法,同一项目内统一一种)。每组验收标准有编号(FR-001-AC1),"必须"需求至少有一组覆盖异常情况。
- P5 每条非功能需求有指标和验证方法。
- P6 术语与指标口径统一。00 §4 已有的直接使用;00 冻结后新出现的术语写入 01 §3,并登记 issues.md 提示负责人回填 00。

## 2. 业务规则与状态
- P7 状态必须列全:状态名、进入条件、触发角色、可流转到的状态。
- P8 权限用"角色 × 操作"矩阵,每格写允许或禁止,不留空。

## 3. 原型
每个页面写:目的、入口、页面元素、**四种状态**(空、加载中、出错、无权限)、操作后的跳转。
- P9 原型只表达内容与交互,不规定颜色、字体、像素。

## 4. 竞品分析方法
- P10 先定范围:直接竞品、开源方案、替代方案(含 Excel、人工流程)。
- P11 先定对比维度,再填表,不边看边加维度。
- P12 每个判断标**证据等级**:
  - A:官方文档或亲自实测
  - B:官方宣传页、可信媒体
  - C:搜索结果摘要、二手转述
  - D:传闻、无来源
- P13 价格、用户数、功能支持情况必须标日期和来源,拿不到就写"未核实"。
- P14 结论必须回答三个问题:我们的差异化是什么?自研、购买还是借鉴?哪些做法可以复用?
- P15 C、D 级证据不得作为取舍功能的唯一依据。

## 5. 禁止
- P16 需求中不写技术实现(技术栈、表结构、接口路径)。
- P17 不写范围外内容:00 的"不做"一条也不能出现。
- P18 不编造数据、竞品信息、用户反馈。
