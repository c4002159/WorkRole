## 变更模式(首次上线后)
任务由"CHG-xxx"开头的消息触发。你只写 `docs/changes/CHG-xxx-名称/02-delta.md`、`src/`、`tests/unit/` 与依赖配置,**不得修改 `docs/00` 至 `docs/04` 基线**。
1. 先读该变更的 proposal 与已冻结的 01-delta,再读基线 02 里受影响的数据模型与接口。
2. 02-delta 必须写:数据迁移脚本(可回滚)、接口变更是否向后兼容、新增任务表、本次需求覆盖表、回滚方案。proposal 里产品只引用了技术条目的名称,**技术影响评估由你在 02-delta 里补齐**。接口契约增量写在 02-delta §2(你不能写 `docs/openapi.yaml`,由我归档时合并)。
3. 任务编号延续基线;其余编码规则与初版阶段相同。
4. 迁移或接口变更可能影响已上线数据、已有调用方时,写入 issues.md(类型"变更请求")并停下等我确认。

## 契约变更流程(接口契约或数据模型需要改时)
1. **停下**,在 issues.md 写一条类型为"变更请求"的问题,说明改什么、为什么、影响谁。
2. 等我授权。**未经授权不得修改。**
3. 初版阶段:我把 02 的状态改回"待确认",你修订 02 并重新提交,我再冻结,然后继续编码。
4. 变更阶段:走新的变更文件夹(CHG-xxx),契约增量写在 `02-delta.md` §2,C2 冻结后才能按新契约编码。归档时由我把增量合并进 `docs/openapi.yaml`。

## 禁止
- 修改 00、01、03、04 和 `tests/acceptance/`。
- 擅自修改已冻结的接口契约和数据模型(流程见上面"契约变更流程")。
- 新增依赖,除非任务里明确写了。
- 为了通过测试而修改、删除、跳过测试或放宽断言。
- 做任务以外的功能,或"顺手"重构。
- 把密钥、账号、真实数据写进代码或提交。
- 自己设计视觉样式:按 02 里的界面规范,使用选定的组件库。
