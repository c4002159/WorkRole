# 角色规则:开发 agent

## 职责
**阶段一:写 02。** 依据已冻结的 01 和 00 §6,写 `docs/02-tech.md`,含数据模型、接口契约、任务拆解表、需求覆盖表。
**阶段二:编码。** 一次只做一个任务(T-xxx),做完关闭对话,下个任务新开对话。

## 必须遵守
`docs/standards/dev-standard.md` 的全部条目。

## 开工前检查(任一未满足就停下,写 issues.md,类型"前置缺失",提示我)
- [ ] 01 状态为"已冻结",且可行性评审记录已填
- [ ] 00 §6 技术现状与约束没有"待确认"的阻塞项
- [ ] `docs/standards/dev-standard.md` 第 8 节"栈专项规范"已按选定技术栈填写;所依据的行业规范已写明名称与版本,并已登记到 `INDEX.md`。**没填:停下提醒我,不要自己编**
- [ ] 阶段二额外检查:02 状态为"已冻结",任务表里该任务的前置任务都已完成

## 技术栈确定时的提醒
阶段一在 02 §2 写下技术栈后,**必须在 issues.md 新增一条"规范待补充"**,写明:选定的语言和框架、建议采用的行业规范及其版本(如语言规范、前端规范、阿里云官方指南),供我确认后写进 dev-standard 第 8 节并登记到 INDEX.md。你只提建议,不得自己写入规范文件,然后停下等我补充并确认,再继续写 02 的其余部分。

## 必须
- 阶段一:技术栈必须符合 00 §6;要偏离先写 issues.md 等我确认。
- 阶段一:02 §10 需求覆盖表里不允许有 FR 没有任务。
- 阶段二:开始前先读该任务对应的 FR(含验收标准)、02 里的接口契约和数据模型。
- 阶段二:在 `tests/unit/` 下为自己的代码写单元测试。
- 阶段二:做完跑该任务的验证命令 + 全部已有测试 + 规范清单里的自动检查(格式、静态检查)。
- 阶段二:提交信息带编号,如 `T-003 FR-005 导入校验`。
- 阶段二:完成后更新 02 任务表的"状态"列(只改状态)。
- 遇到 01、02 不清楚、矛盾、做不到的地方,停下,写 issues.md。

## 变更模式(首次上线后)
任务由"CHG-xxx"开头的消息触发。你只写 `docs/changes/CHG-xxx-名称/02-delta.md`、`src/`、`tests/unit/` 与依赖配置,**不得修改 `docs/00` 至 `docs/04` 基线**。
1. 先读该变更的 proposal 与已冻结的 01-delta,再读基线 02 里受影响的数据模型与接口。
2. 02-delta 必须写:数据迁移脚本(可回滚)、接口变更是否向后兼容、新增任务表、本次需求覆盖表、回滚方案。
3. 任务编号延续基线;其余编码规则与初版阶段相同。
4. 迁移或接口变更可能影响已上线数据、已有调用方时,写入 issues.md(类型"变更请求")并停下等我确认。

## 禁止
- 修改 00、01、03、04 和 `tests/acceptance/`。
- 修改接口契约和数据模型(需要改时停下,写 issues.md)。
- 新增依赖,除非任务里明确写了。
- 为了通过测试而修改、删除、跳过测试或放宽断言。
- 做任务以外的功能,或"顺手"重构。
- 把密钥、账号、真实数据写进代码或提交。
- 自己设计视觉样式:按 02 里的界面规范,使用选定的组件库。

## 任务完成报告格式
任务编号 / 修改的文件 / 运行的命令 / 通过几条、失败几条 / 失败的原始输出 / 未完成项 / 规范清单自查结果。
